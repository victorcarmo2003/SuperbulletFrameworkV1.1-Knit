01 — Foundations

Before we start: how a Roblox game is actually built

A Roblox game is a collection of scripts — small programs, written in a language called Luau — attached to a 3D world. When someone plays the game, two very different copies of it run at once:

The Server
  • Runs on a computer owned by Roblox, not the player.
  • One single copy, shared by everyone in that game session.
  • Nobody can see its code or tamper with it while playing.
  • This is where the game decides what's actually true — health, currency, inventory.
The Client
  • Runs on each player's own device.
  • One copy per player — what they see, hear, and click.
  • A player with cheat software can freely read and rewrite this copy.
  • It only ever asks the server for things; it can't be trusted to decide them.

Keep that split in your head — server decides, client displays and asks — because almost every rule in this framework exists to protect it. You'll see it again in Security basics.

02 — Origins

What is Knit?

Knit is a widely-used open-source library that gives Roblox scripts a consistent shape. Instead of every script inventing its own way of organizing code, Knit defines two building blocks:

  • Service — a piece of server-side logic with a name, like ShopService or QuestService.
  • Controller — the client-side counterpart, like DataController.

Knit also gives services and controllers a predictable startup sequence and an easy way to talk to each other and to the other realm (server ↔ client), instead of everyone wiring up RemoteEvents by hand.

03 — This project

Why Superbullet forked Knit

SuperbulletFrameworkV1-Knit takes Knit and wraps it with stricter, more predictable rules on top. The goal stated in this project is to be beginner-friendly and to be operable mainly by an AI trained on it (an internal tool called SuperbulletAI). Two priorities follow from that:

Design priority

Clarity over elegance. Errors that teach, patterns that are predictable, as little framework "magic" as possible — so both a human beginner and an AI reading the code can guess correctly what a piece of code does before running it.

In code terms, that means: a fixed folder shape for every system, a strict rule about which files are allowed to talk to which, and a hard line never to skip when writing something a player's device could exploit. The rest of this page walks through each of those rules.

04 — Core pattern

Services & Controllers: the anatomy of a system

Every Service or Controller — together just called a system here — starts as one file, init.lua. If it grows past roughly 300 lines, its logic gets split into three kinds of helper files sitting in a Components/ folder next to it: 

ShopService/
├── init.lua          ← the system itself, always runs first
└── Components/
    ├── Accessor.lua  ← read-only: "give me the price of item X"
    ├── Mutator.lua   ← write: "give this player item X"
    └── Others/
        └── DiscountCalculator.lua

A small system (under ~100 lines, simple reads/writes) skips this split entirely — the folder structure is overhead you only pay for once a system is actually big enough to need it.

The one rule that's checked automatically, on every save, is who is allowed to call whom:

Communication matrix
FromAccessorMutatorOthers
Accessor.lua—blockedallowed
Mutator.luablocked—allowed
Others/*.luaonly through init.lua, never sideways

Reads and writes never call each other directly — if a read needs to trigger a write, that decision is made by init.lua, the one file allowed to talk to everyone. A script (check-architecture.luau) scans the whole codebase and fails loudly if a file breaks this rule.

Golden rule of startup

The function that runs first on any system, Init, is never allowed to wait for anything — no pausing for an asset to load, no pausing for a network call. If it did, it would freeze the startup of the entire game for every other system too. Anything that needs to wait belongs in the function that runs second, Start.

05 — A second pattern

Behaviors & Mixins: code attached to objects

Services and Controllers are singular — one ShopService for the whole game. But some logic needs to run on every object of a certain kind scattered around the 3D world: every pickup, every door, every damage zone. For that, the framework uses a second, different pattern called a Behavior.

A game designer marks any object in the world with a Tag — a plain text label like "Pickup" — using Roblox Studio's built-in Tag Editor, no code required. A matching PickupBehavior.lua file then automatically attaches its logic to every object carrying that tag, however many there are.

When two unrelated Behaviors need to share some logic (say, both a pickup and a door need to show a floating "Press E" prompt), that shared piece lives in a Mixin — a plain helper table, called explicitly, never merged in automatically.

06 — What players see

The Interface layer

On-screen menus, health bars, and buttons are built with Vide, a reactive UI library. "Reactive" means a component is written once as a function of its current data, and the screen updates itself automatically whenever that data changes — nobody manually writes "now redraw the health bar."

Components are previewed in isolation using a Roblox Studio plugin called UI Labs, so a designer can tweak how a progress bar looks without needing a full game session running.

07 — Persistence

Player data: how progress is saved

Anything that must survive a player leaving and coming back — level, currency, inventory — is called their profile, saved through a library called ProfileService. Three rules protect it from corruption:

  1. Code never edits saved data directly — it always goes through one function that logs the change and knows how to detect it.
  2. Adding a brand-new field (say, a new setting) is done in one template file first; every existing player's save file is then automatically patched to include it.
  3. A player's own device can only read their data, never write it — every change is requested from the server and validated there. See the next section for why.
08 — The rule that can't bend

Security basics: never trust the client

Recall the split from the top of this page: a player's device can be freely rewritten by cheat tools. So any message that arrives from a client is treated as something a stranger typed, not as fact — no matter how the request looks in the original code.

Never do this

Client sends a number: AddPoints:Fire(99999)
— an exploiter can send any number they like.

Do this instead

Client sends an intention: TurnInQuest:Fire(questId)
— the server looks up the quest and decides the reward itself.

In short: a client is only ever allowed to say what it wants to happen. The server is the only place that says how much and whether it's allowed.

09 — Developer tooling

The AI debug bridge

A pair of systems, SuperbulletServerLogger and SuperbulletClientLogger, exist purely to help while building the game inside Roblox Studio. They batch up logs and send them over a WebSocket connection to the external SuperbulletAI desktop app — the same AI this framework is designed to be operated by — so it can see what's happening without a human copy-pasting the Output window. This bridge is Studio-only; it never ships in the real, published game.

11 — The command line

The toolchain, in plain English

Rojo
Turns the folders and files above into a real Roblox place, kept in sync with Studio as you edit.
Rogen
Generates Rojo's project file from a simpler config, so folder structure doesn't have to be edited by hand.
Wally
Downloads third-party Luau libraries this project depends on — comparable to npm for JavaScript.
rokit
Installs the exact same version of every command-line tool for everyone on the team.
selene
A linter — reads code without running it and flags likely mistakes.
lune
Runs Luau scripts standalone, outside of Roblox — used to check the communication matrix above.
12 — Reference

Glossary

Roblox
The game platform and engine this entire project builds on top of.
Luau
The programming language Roblox scripts are written in, a dialect of Lua.
Script
A single file of Luau code that Roblox runs.
Server / Client
The two realms every multiplayer Roblox game runs in — see the top of this page.
Service / Controller
Knit's names for a server-side / client-side system.
RemoteEvent
Roblox's mechanism for sending a message between server and client.
CollectionService
Roblox's built-in system for grouping objects under a shared Tag.
Tag
A plain-text label placed on an object in Studio, with no code required.
ProfileService
The library this project uses to save and load player data safely.
Exploiter
A player using modified software to read or rewrite their own client.
Linter
A tool that reads code for likely mistakes without running it.
